# CMS Guard Lite 로컬 웹 UI 설계

- 작성일: 2026-10-15
- 대상 버전: CMS Guard Lite v0.2 계획
- 상태: 사용자 승인 완료

## 1. 목적

CMS Guard Lite의 기존 명령줄 점검 엔진에 로컬 웹 API를 추가하고, 별도 Vue 프론트엔드에서 실제 CMS 권한 점검과 연구용 비교 실험을 실행·확인한다. 첫 버전은 한 사용자가 자신의 PC에서만 사용하는 로컬 도구다. 외부 접속, 다중 사용자, 분산 스캔은 지원하지 않는다.

성공 기준은 다음과 같다.

- `python -m cms_guard web` 명령 하나로 API와 빌드된 UI를 시작하고 브라우저를 연다.
- 기존 명령줄 사용법과 기존 40개 테스트를 유지한다.
- 실제 CMS 점검과 연구 비교 실험을 안내형 UI에서 분리해 제공한다.
- 환경변수 인증과 UI 일회성 인증을 모두 지원한다.
- 모든 실행 이력을 SQLite에 보관하되 실제 URL·인증정보·응답 원문·canary 원문은 저장하지 않는다.
- UI와 API는 기본적으로 `127.0.0.1`에서만 통신한다.

## 2. 저장소와 구성요소

## 3. 실행 구조

`python -m cms_guard web`은 다음을 수행한다.

1. FastAPI를 `127.0.0.1:8787`에 바인딩한다.
2. `web_dist/`의 정적 UI를 제공한다.
3. 실행 시점에 로컬 세션 토큰을 생성한다.
4. 준비 완료 후 기본 브라우저를 연다.
5. 종료 신호를 받으면 진행 중 작업과 서버를 정리한다.

개발 명령은 다음과 같이 분리한다.

```bash
python -m cms_guard api
npm run dev
```

동시에 하나의 점검 또는 벤치마크만 실행한다. 실행 중 새 작업 요청은 대기열에 넣지 않고 HTTP 409와 사용자용 안내를 반환한다.

## 4. 안내형 UI

첫 화면은 두 가지 작업을 큰 선택 카드로 보여준다.

1. 실제 CMS 점검
2. 연구 비교 실험

그 아래에는 최근 실행의 유형, 시각, 상태별 결과 수, 요청 수, 실행 시간과 보고서 진입점을 표시한다.

### 4.1 실제 CMS 점검 흐름

실제 점검은 네 단계로 진행한다.

1. **범위 설정**: 비식별 별칭, CMS Origin, 요청·시간·속도 제한, 허용 네트워크
2. **역할·인증**: 역할, Cookie/Bearer, 환경변수 또는 일회성 입력
3. **테스트 대상**: 종류, 정확한 URL, canary, 역할별 allow/deny, 세션 회수 확인
4. **검토·실행**: URL 수, 역할 수, 최대 요청, 읽기 전용 여부, 자격정보 비저장 상태 확인

실행 중 화면은 대상별 `대기`, `요청 중`, `기대 충족`, `위반 발견`, `판정 보류`, `실행 오류`를 표시한다. 중단 요청을 받으면 새 HTTP 요청을 시작하지 않고 완료된 결과를 `cancelled` 실행으로 보관한다.

결과 화면은 `pass`, `fail`, `inconclusive`, `error`, `manual` 집계를 표시하고 대상 별칭·역할·판정·HTTP 상태·canary 확인 여부·응답 시간·판정 이유를 제공한다. 결과 검색, 상태 필터, 실행 비교와 JSON·Markdown·HTML 보고서 다운로드를 지원한다.

### 4.2 연구 비교 흐름

연구 화면은 정상 fixture와 취약 fixture를 동일 조건으로 1~20회 실행한다. TP·FP·FN·TN, precision, recall, unresolved, 평균 실행 시간, 평균 요청 수와 실행별 편차를 표시한다.

모든 연구 화면과 내보낸 결과에는 합성 사례 결과이며 실제 서비스 성능이나 PentAGI 대비 우수성을 뜻하지 않는다는 문구를 표시한다.

### 4.3 실행 이력

모든 실행은 보관한다. 날짜·유형·판정으로 검색하고 과거 결과 열기, 두 실행 비교, 개별 삭제, 전체 이력 JSON 내보내기를 지원한다. 삭제 전 확인을 요구하며 해당 실행의 보고서도 함께 삭제한다.

## 5. API

| 방식 | 경로 | 기능 |
|---|---|---|
| `GET` | `/api/health` | API 상태 |
| `POST` | `/api/config/validate` | 설정 검증, 네트워크 요청 없음 |
| `POST` | `/api/runs` | 실제 CMS 점검 시작 |
| `POST` | `/api/demos` | 정상·취약 데모 시작 |
| `POST` | `/api/benchmarks` | 반복 비교 실험 시작 |
| `GET` | `/api/runs/{id}` | 상태와 결과 조회 |
| `POST` | `/api/runs/{id}/cancel` | 실행 중단 요청 |
| `GET` | `/api/runs` | 이력 검색 |
| `GET` | `/api/runs/{id}/reports/{format}` | 보고서 다운로드 |
| `DELETE` | `/api/runs/{id}` | 실행과 보고서 삭제 |

첫 버전의 진행 상황은 1초 폴링으로 조회한다. WebSocket과 SSE는 사용하지 않는다.

작업 상태는 `queued`, `running`, `completed`, `cancelled`, `failed`로 관리한다. 점검 결과 상태와 작업 상태를 분리한다. 취약점 위반이 발견돼도 작업이 정상 종료되면 작업 상태는 `completed`다.

API는 기존 `config.validate`, `engine.run`, `benchmark.benchmark`, `report.write_report`와 로컬 demo fixture를 호출한다. 점검 HTTP 로직은 API 계층에서 다시 구현하지 않는다.

## 6. 인증정보 처리

환경변수 방식에서 API는 값의 존재 여부만 UI에 반환한다. 값 자체는 반환하지 않는다.

일회성 입력 방식은 다음 규칙을 따른다.

- 브라우저 자동완성과 영구 저장을 사용하지 않는다.
- 값은 `127.0.0.1` API에만 전달한다.
- API 작업 전용 메모리에만 보관한다.
- 실행 완료·중단·오류 시 참조를 제거한다.
- 로그, SQLite, 보고서, 오류 응답에 기록하지 않는다.
- 페이지 새로고침 시 UI 상태에서 제거한다.

기존 `credentials()`는 선택적인 메모리 자격정보 매핑을 받을 수 있도록 확장한다. 전달하지 않으면 기존 환경변수 동작을 그대로 사용한다.

## 7. 데이터 저장

SQLite는 다음 테이블을 사용한다.

| 테이블 | 저장 내용 |
|---|---|
| `runs` | UUID, 유형, 작업 상태, 시작·종료 시각, 상태별 집계 |
| `results` | 실행 UUID, 대상 별칭, 역할, 판정, 제한된 증거 |
| `metrics` | 요청 수, 실행 시간, 벤치마크 지표 |
| `reports` | 형식, 서버가 생성한 상대 경로 |

실제 URL은 저장하지 않고 실행 중 계산한 SHA-256 지문만 저장한다. 지문은 동일 대상 비교에만 사용하며 URL을 복구할 수 있는 암호화나 매핑을 보관하지 않는다. 자격정보, 환경변수 값, 응답 원문과 canary 원문은 저장하지 않는다.

## 8. 로컬 보안 경계

- API는 `127.0.0.1`에만 바인딩한다.
- Vite 개발 Origin과 배포 UI Origin만 CORS로 허용한다.
- 서버 시작 시 예측 불가능한 세션 토큰을 만들고 변경 API에서 검증한다.
- JSON 요청 크기를 제한하고 지원하지 않는 Content-Type을 거부한다.
- 사용자가 파일 경로나 보고서 경로를 직접 지정하지 못하게 한다.
- 실행·보고서 식별자는 서버가 발급한 UUID만 허용한다.
- 디버그 모드는 기본 비활성화한다.
- 오류 응답은 범주형 코드와 사용자용 메시지만 제공한다.
- 로그에 URL, 자격정보, 응답 본문과 canary를 기록하지 않는다.
- 기존 엔진의 정확한 URL 범위, HTTPS, DNS/IP, 요청 수, 시간, 응답 크기 제한을 유지한다.

## 9. 오류 처리

- API 미실행: 실행 명령과 로컬 서버 상태 안내
- 인증정보 누락: 누락된 환경변수 또는 역할만 표시
- 연결 실패: 네트워크·DNS·인증서 확인 안내
- 양성 대조군 실패: URL·계정·canary 확인 안내
- 응답 크기 초과: 판정 보류와 제한 조정 안내
- 시간 초과: 판정 보류 또는 실행 오류로 구분
- 동시 실행: HTTP 409와 현재 작업 종료 안내
- 사용자 중단: 완료 결과 보존, 작업 상태 `cancelled`
- 보고서 실패: 점검 결과 보존, 재생성 허용
- DB 기록 실패: 실행 중단, 메모리 인증정보 폐기

사용자 오류 화면과 일반 로그에 내부 예외 문자열을 그대로 노출하지 않는다.

## 12. 향후 확장 기준

개인용 로컬 도구에서 다중 사용자 또는 분산 실행으로 요구가 바뀌면 API를 별도 저장소로 분리한다. 그때 사용자 인증, 권한, 감사 로그, 작업 큐, 노드 등록·인증, 전송 암호화와 중앙 데이터베이스를 새 설계로 다룬다. 첫 버전에는 미래 기능을 위한 Redis·MongoDB·분산 추상화를 미리 넣지 않는다.
